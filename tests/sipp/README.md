# SIPp-сценарии

Регресс сигнализации на живом стенде. SIPp не входит в образы — установите его
на хосте (`apt install sip-tester` / `pacman -S sipp`) или запускайте в
контейнере.

## Файл данных

`subscribers.csv` содержит набираемый прокси-номер (`[field0]`). Формат SIPp:
первая строка `SEQUENTIAL`, дальше строки с полями через `;`.

Скопируйте `subscribers.csv.example` в `subscribers.csv` и подставьте номер,
выданный `POST /sessions`. Пароли в файле не нужны — digest-учётные данные
передаются ключами `-au` / `-ap`, потому что SIPp не подставляет `[field]`
внутрь тега `[authentication]`.

## Запуск

```bash
# 1. Активная сессия должна соединяться.
#    Заранее: POST /sessions для пары A/Б, софтфон Б зарегистрирован
#    и отвечает на OPTIONS (иначе qualify пометит контакт Unavailable
#    и Asterisk не сможет набрать второе плечо).
sipp -sf uac_connected.xml -inf subscribers.csv \
     -s 77011234567 -au 77011234567 -ap "$SIP_A_PASSWORD" \
     -m 1 -timeout 60 -trace_err 127.0.0.1:5060

# 2. Истёкшая/закрытая сессия и неизвестный звонящий: подсказка и отбой.
#    Заранее: DELETE /sessions/{id} либо звонок с номера без сессии.
sipp -sf uac_rejected.xml -inf subscribers.csv \
     -s 77015550022 -au 77015550022 -ap "$SIP_C_PASSWORD" \
     -m 1 -timeout 60 -trace_err 127.0.0.1:5060
```

`-s` — SIP-пользователь, от имени которого идёт вызов; имя эндпоинта в
`pjsip.conf` совпадает с цифрами номера абонента, поэтому `-s` и `-au`
одинаковые.

## Как читать результат

* `uac_connected.xml`: успешный прогон — `Successful call` = 1. Но сам по себе
  он **не отличает** соединение от подсказки: отказ тоже начинается с `200 OK`.
  Решающая проверка — журнал: `status=answered` и ненулевая `duration_sec`.
* `uac_rejected.xml`: успешный прогон — сценарий получил `200 OK`, затем `BYE`
  от Asterisk. Если `BYE` не пришёл за 30 секунд, сервис соединил вызов,
  который обязан был отклонить, — это дефект приватности, а не таймаут.

После каждого прогона проверяйте журнал:

```bash
curl -sS -H "X-API-Key: $API_KEY" 'http://127.0.0.1:8000/api/v1/calls?limit=5'
```

Ожидаемые `status`: `answered` для первого сценария, `expired` или
`unknown_caller` — для второго.

## Ограничение SIPp как второго абонента

SIPp в режиме UAS не умеет одновременно отвечать на OPTIONS (`-oocsf`
несовместим с server-режимом), поэтому `qualify_frequency=30` из
`pjsip.conf` пометит его контакт как `Unavail`, и Asterisk откажется набирать
второе плечо с ошибкой `Allocation failed`. Для полностью автоматического
прогона входящего плеча используйте настоящий софтфон либо временно задайте
`qualify_frequency=0` для AOR абонента Б.
