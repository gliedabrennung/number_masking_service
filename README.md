# Сервис маскировки телефонных номеров — прототип

Голосовая связь между двумя абонентами через прокси-номер: ни одна из сторон не
видит реальный номер другой. Классические сценарии — курьер и получатель,
водитель и пассажир, покупатель и продавец на маркетплейсе.

**Стек:** Asterisk 22 LTS (chan_pjsip) + ARI · Python 3.12+ / FastAPI · PostgreSQL 16 ·
Redis 7 · Docker Compose.

Разделы: [архитектура](#архитектура), [как это
работает](#как-это-работает), [API](#api), [ограничения
прототипа](#ограничения-прототипа), [переход в
продакшн](#переход-в-продакшн).

---

## ⚠️ Требование к хосту

Стенд разворачивается **только на Linux-хосте или Linux-VM**.

Контейнер Asterisk работает в режиме `network_mode: host`: пробрасывать
диапазон RTP-портов через bridge-сеть Docker непрактично, а ARI-сокет обязан
оставаться на loopback. Docker Desktop для macOS/Windows не даёт нужного
host-networking — сигнализация поднимется, а звук не пойдёт.

### Настройка софтфонов

Zoiper 5 / Linphone / MicroSIP, два аккаунта (третий — для сценария с
добавочным кодом):

| Поле | Значение |
|---|---|
| Domain / server | IP-адрес хоста со стендом |
| Username | `77011234567` (A), `77019876543` (Б), `77015550022` (В) |
| Password | из `.env` (`SIP_A_PASSWORD`, `SIP_B_PASSWORD`, `SIP_C_PASSWORD`) |
| Transport | UDP, порт 5060 |

Эндпоинты названы по цифрам собственного номера — это то, что ожидает
`ENDPOINT_TEMPLATE=PJSIP/{digits}`. При переходе на транк оператора шаблон
меняется на `PJSIP/{number}@trunk-operator`, код не меняется.

### Демо-сценарий

```bash
# 1. создать сессию
curl -sS -X POST http://127.0.0.1:8000/api/v1/sessions \
  -H 'Content-Type: application/json' -H "X-API-Key: $API_KEY" \
  -d '{"party_a":"+77011234567","party_b":"+77019876543","ttl_seconds":3600}'
# -> {"proxy_number":"+77172000101", ...}

# 2. с софтфона A набрать +77172000101 — звонит Б, на экране Б прокси-номер
# 3. с софтфона Б набрать тот же номер — звонит A, на экране A прокси-номер

# 4. журнал
curl -sS -H "X-API-Key: $API_KEY" \
  http://127.0.0.1:8000/api/v1/sessions/<session_id>/calls
```

## Архитектура

```
   HTTPS          ┌──────────────────────────┐
 ───────────────▶ │ masking-app (FastAPI)    │
  POST /sessions  │ • выдача номеров         │
                  │ • TTL, журнал            │
                  │ • Stasis-приложение ARI  │
                  └───┬───────────┬──────────┘
                      │           │ ws + REST
       ┌──────────────┴──┐   ┌────▼──────────────┐
       │ PostgreSQL      │   │ Asterisk 22 LTS   │
       │ sessions        │   │ chan_pjsip        │
       │ numbers, calls  │   │ bridge / RTP-релей│
       └─────────────────┘   └────┬──────────────┘
       ┌─────────────────┐        │ SIP/RTP
       │ Redis (кеш      │   ┌────┴─────┬─────────┐
       │ маршрутов, RL)  │   ▼          ▼         ▼
       └─────────────────┘  Софтфон A  Софтфон Б  ...
```

**Ключевой принцип:** в dialplan Asterisk нет ни одной строки бизнес-логики —
только передача вызова в Stasis. Решение о маршруте принимает приложение по
данным из БД. Поэтому подключение реального SIP-транка — это смена SIP-эндпоинта,
а не переписывание логики. Весь dialplan — шесть строк на контекст.

### Разделение ответственности

| Компонент | Отвечает за | Не отвечает за |
|---|---|---|
| `masking-app` (FastAPI) | CRUD сессий, выдачу номеров, валидацию E.164, аутентификацию, журнал, Stasis-обработчик ARI | SIP-сигнализацию и медиа |
| Asterisk 22 LTS (chan_pjsip) | SIP, RTP-релей, транскодинг, воспроизведение подсказок, DTMF | Любые решения о маршруте |
| PostgreSQL 16 | Источник истины: `numbers`, `sessions`, `session_parties`, `calls` | — |
| Redis 7 | Кеш маршрутов, rate limit | Долговременное хранение |

Управляющее приложение и Stasis-обработчик по умолчанию живут в одном процессе
(`RUN_ARI_IN_API=true`) и разделяют слой бизнес-логики. Разнесение на два
контейнера — смена переменной окружения, кода не касается.

Поиск сессии идёт по ключу `(прокси, HMAC(звонящий))` независимо от роли
абонента, поэтому обратное направление (Б → A) не требует отдельного кода:
направление вычисляется по найденной роли.

## Как это работает

### Выдача номера

Один прокси-номер обслуживает **много пар одновременно**. Единственное
ограничение: один и тот же абонент не может иметь две активные *эксклюзивные*
сессии на одном номере — иначе обратный поиск «кто звонит → с кем соединять»
станет неоднозначным. Инвариант защищён частичным уникальным индексом
`uniq_active_party_per_number`.

Выдача идёт в одной транзакции с `SELECT ... FOR UPDATE SKIP LOCKED`, поэтому
параллельные `POST /sessions` не могут получить один и тот же номер в конфликте.

### Cooldown

Освобождённый номер не выдаётся заново `NUMBER_COOLDOWN_HOURS` (по умолчанию 24).
Причина: абонент может перезвонить по истории вызовов через несколько часов и
попасть к постороннему человеку.

Два режима (`COOLDOWN_SCOPE`):

* `number` (по умолчанию) — карантин номера для всех.
* `party` — карантин только для абонентов закрытой сессии. Точнее по смыслу и
  экономнее для пула; рекомендуется в продакшене при большом пуле.

Карантин по абоненту применяется **всегда**, независимо от режима.

### Добавочные коды (DTMF)

Если свободного номера для пары нет, сессия получает общий номер и 4-значный
PIN. Тогда по `(прокси, звонящий)` находится больше одной активной сессии, и
приложение спрашивает код.

Отсюда следует неочевидное требование: **все** активные сессии этого абонента на
этом номере обязаны иметь PIN, иначе сессия без PIN станет недостижимой. Поэтому
выдача с PIN автоматически присваивает код и уже существующим сессиям этого
абонента на этом номере; их идентификаторы возвращаются в поле
`promoted_session_ids` и уходят в вебхук `session.updated`.

Режим управляется `EXT_CODE_MODE`:

| Значение | Поведение |
|---|---|
| `auto` (по умолчанию) | сначала эксклюзивный номер, при исчерпании — общий с PIN |
| `always` | PIN у каждой сессии; единообразный UX, «повышений» не бывает |
| `never` | вместо общего номера — `409 no_number_available` |

Если по `(прокси, звонящий)` найдена ровно одна сессия, код не спрашивается,
даже если он у сессии есть: выбирать не из чего, и вторая сторона общей сессии
соединяется без лишних действий.

### Приватность

* `From` исходящего плеча — всегда прокси-номер (`callerId` в originate).
* `send_pai=no`, `send_rpid=no`, `send_diversion=no`, `trust_id_outbound=no`.
* `direct_media=no` — RTP всегда через Asterisk, иначе абоненты обменялись бы
  IP-адресами.
* Реальные номера в БД — только в виде AES-256-GCM шифротекста; поиск идёт по
  `HMAC-SHA256(номер, PARTY_HASH_SECRET)`.
* В логах номера маскируются (`+7701***4567`) на двух уровнях: в местах вызова и
  сквозным процессором structlog, который перепроверяет каждое поле.
* В таблице `calls` реальных номеров нет вообще — только `caller_hash`.
* Запись разговоров невозможна технически: не загружаются ни `app_record.so`
  с `app_mixmonitor.so`, ни ARI-модули записи (`res_stasis_recording`,
  `res_ari_recordings`, `res_pjsip_one_touch_record_info`) — см.
  `asterisk/conf/modules.conf`. Каталоги `recording` и `monitor` в спуле
  удаляются при старте контейнера, полей под аудиофайлы в схеме нет.
* Display-name звонящего стирается на входящем канале (`CALLERID(name)`), а
  исходящее плечо получает прокси-номер и в номере, и в имени: софтфон обычно
  пишет в display-name собственный номер абонента.

Шифрование выполняется в приложении, а не в БД: ключ тогда не попадает на
сервер PostgreSQL, в `pg_stat_activity` и в логи запросов. Форма хранения от
этого не зависит (`BYTEA`).

### Хранение данных

Журнал звонков — 90 дней, закрытые сессии — 30 дней; удаляет фоновая задача,
интервалы в конфиге (`CALL_RETENTION_DAYS`, `CLOSED_SESSION_RETENTION_DAYS`).

## API

Базовый путь `/api/v1`, аутентификация — заголовок `X-API-Key`, rate limit 60
запросов в минуту на ключ, тело запроса ≤ 8 КБ.

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/sessions` | создать сессию, получить прокси-номер |
| `GET` | `/sessions/{id}` | состояние сессии (номера маскированы) |
| `GET` | `/sessions` | список с фильтрами `status`, `external_id` |
| `PATCH` | `/sessions/{id}` | продление TTL |
| `DELETE` | `/sessions/{id}` | досрочное закрытие (активный разговор не рвётся) |
| `GET` | `/sessions/{id}/calls` | журнал звонков сессии |
| `GET` | `/calls` | сводный журнал, фильтры `from`, `to`, `status`, пагинация |
| `GET` | `/numbers` | состояние пула: всего / занято / в cooldown |
| `POST` | `/numbers` | добавить номер в пул |
| `PATCH` | `/numbers/{e164}` | включить / выключить номер |
| `GET` | `/health`, `/ready`, `/metrics` | liveness, readiness (включая ARI), Prometheus |

Коды ошибок: `401` (ключ), `409 no_number_available`, `409 session_not_active`,
`413`, `422` (E.164, A == Б), `429`. Тело ошибки:
`{"error": "<код>", "message": "...", "trace_id": "..."}`.

Спецификация: `make openapi` → [`docs/openapi.json`](docs/openapi.json);
коллекция Bruno — [`docs/bruno/`](docs/bruno).

### Вебхуки

При `WEBHOOK_URL` и `WEBHOOK_SECRET` отправляются события `call.started`,
`call.answered`, `call.ended`, `session.expired`, `session.updated`. Подпись —
`X-Masking-Signature: sha256=<hex>`, HMAC-SHA256 по сырому телу. Повторы по
экспоненте, до `WEBHOOK_MAX_ATTEMPTS`.

make install            # зависимости с dev-экстрами

Код следует [Google Python Style
Guide](https://google.github.io/styleguide/pyguide.html).
Что из этого проверяется автоматически (`make lint`, конфигурация в
`pyproject.toml`): длина строки 80, порядок и формат импортов, докстринги в
Google-формате (`D`, секции `Args`/`Returns`/`Raises`), именование (`N`,

Интеграционные тесты работают с отдельной базой `<db>_test`, создают её сами и

Что покрыто: нормализация E.164 и маскирование, крипто, сбор DTMF с таймаутами,

Сценарии SIPp для регресса сигнализации — [`tests/sipp/`](tests/sipp).

### Что проверено на живом стенде

Помимо автотестов сценарии прогоняются через SIPp против настоящего Asterisk:

* соединение A → прокси → Б: журнал `answered`, `duration_sec=5`,
  `direction=a2b`, `hangup_cause=16`;
* в INVITE, доставленном абоненту Б, `From: "+7717…" <sip:+7717…>` — прокси-номер
  и в номере, и в display-name; реальный номер A не встречается в трафике к Б
  ни разу; `P-Asserted-Identity`, `Remote-Party-ID`, `Diversion` отсутствуют;
  `Contact` — адрес Asterisk; RTP-порт из диапазона 10000–10200;
* отказ по неизвестному номеру: `200 OK` → подсказка → `BYE` с причиной 21,
  журнал `unknown_caller`, канал занят 3,9 с (столько же длится подсказка);
* сквозной `trace_id`: `POST /sessions` с `X-Trace-Id` — и все события звонка
  в логах идут под тем же значением.

Проверка RTP в Wireshark на одном хосте неинформативна (обе стороны на
127.0.0.1); `direct_media=no` подтверждается только конфигурацией.

### Голосовые подсказки

Пять подсказок лежат готовыми в `asterisk/sounds/ru/custom/` — образ Asterisk
их только копирует и падает на сборке, если файла нет. Перегенерация и
проверка:

```bash
make sounds         # Piper TTS в контейнере, голос ru_RU-dmitri-medium
make check-sounds   # распознать обратно и сравнить с текстом
```

В телефонном канале 8 кГц синтезированная речь легко становится
неразборчивой, поэтому `make check-sounds` прогоняет файлы через
офлайн-распознаватель и печатает долю узнанных слов — подробности в
[`tests/sounds/`](tests/sounds).

Проверка, что полные номера не попадают в логи:

```bash
make check-leaks
```

## Наблюдаемость

Логи — JSON в stdout, обязательные поля `ts`, `level`, `event`, `trace_id`,
`session_id`, `call_id`, `channel_id`. `trace_id` можно задать заголовком
`X-Trace-Id`, он же возвращается в ответе.

Трассировка сквозная: `trace_id` запроса `POST /sessions` сохраняется в
`sessions.trace_id`, и каждый звонок по этой сессии с момента, когда сессия
найдена, логируется под тем же `trace_id`. Один grep по `trace_id` даёт всю
историю: создание сессии, все вызовы, продление, закрытие.

`/metrics` отдаёт `masking_sessions_active`, `masking_numbers_free`,
`masking_numbers_cooldown`, `masking_calls_total{status}`,
`masking_call_setup_duration_seconds` (гистограмма от входящего вызова до
ответа второй стороны), `masking_calls_in_flight`, `masking_ari_ws_connected`. Метрики каналов и
бриджей отдаёт встроенный `res_prometheus` Asterisk на
`http://127.0.0.1:8088/metrics` (тот же loopback-сокет, что и ARI, наружу не
публикуется).

Штатный CDR Asterisk включён как резервный источник для разбора инцидентов;
источник истины — таблица `calls`, привязанная к `session_id`.

## Безопасность стенда

* ARI (8088) слушает только `127.0.0.1` — пользователь ARI может инициировать
  вызовы и читать любые каналы.
* Анонимные SIP-вызовы не принимаются, пароли эндпоинтов ≥ 16 символов
  (генерируются `make secrets`).
* fail2ban: `asterisk/conf/logger.conf` пишет `/var/log/asterisk/messages`
  внутри контейнера (том `asterisk-log`); готовые фильтр и jail —
  в [`deploy/fail2ban/`](deploy/fail2ban), инструкция по установке в шапке
  файла фильтра.
* TLS для REST — профиль `caddy`: `docker compose --profile tls up -d`.
* SIP TLS и SRTP в прототипе не включены (см. ограничения).

## Ограничения прототипа

1. Нет интеграции с оператором связи — только SIP-софтфоны в локальной сети/VPN.
2. Один экземпляр Asterisk, без отказоустойчивости; перезапуск рвёт разговоры.
3. Нет тарификации, биллинга, антифрода.
4. Нет SMS-маскирования.
5. Нет веб-интерфейса администратора — управление только через REST API.
6. Кодеки не оптимизированы, транскодинг opus↔alaw под нагрузкой не проверялся.
7. Нагрузочного тестирования не было; ориентир — до 20 одновременных разговоров.
8. Нет TLS/SRTP на SIP-уровне.
9. Нет конференций, перевода вызова, удержания.
10. Стенд требует Linux-хоста: Asterisk работает в `network_mode: host`, так как
    проброс диапазона RTP через bridge-сеть Docker непрактичен.
11. Перезапуск `masking-app` без перезапуска Asterisk может оставить в
    Asterisk устаревшую регистрацию Stasis-приложения: события уходят в
    мёртвое соединение, вызовы молча зависают в Stasis, а `/ready` при этом
    показывает `ari_ws_connected: true`. Лечится `docker compose restart
    masking-app` (повторно) либо перезапуском Asterisk; в продакшене за это
    отвечает SBC-слой и несколько узлов.
12. Голосовые подсказки синтезированы офлайн-нейросетевым TTS (Piper, голос
    `ru_RU-dmitri-medium`) и лежат в `asterisk/sounds/ru/custom/` (WAV PCM
    16 бит, 8 кГц, моно); разборчиво, но это синтез — для продакшена лучше
    студийная запись диктора.

Юридический риск, фиксируется отдельно: для продакшена в РК потребуется оценка
соответствия Закону «О персональных данных и их защите» и, вероятно, договор на
обработку ПДн с заказчиком.

## Переход в продакшн

Бизнес-логика не меняется. Изменения локализованы:

| Что | Где | Объём |
|---|---|---|
| SIP-транк оператора | `pjsip.conf`: `type=registration` / `type=identify` по IP оператора, `aor`, `endpoint` с контекстом `from-trunk` | новый конфиг, ~30 строк |
| Входящая маршрутизация | `extensions.conf`: контекст `from-trunk` уже есть и вызывает тот же `Stasis(...)` | 0 строк |
| Исходящее плечо | `ENDPOINT_TEMPLATE=PJSIP/{number}@trunk-operator` | переменная окружения |
| Нормализация номеров | `app/core/phone.py` уже приводит `8XXX` → `+77XXX`; при необходимости расширить | unit-тесты |
| CLI | пул прокси-номеров должен быть выделен оператором: подмена CLI блокируется | организационное |
| NAT / firewall | `external_media_address`, `external_signaling_address`, открытие 5060/UDP и диапазона RTP | конфиг + сеть |
| Кодеки | многие операторы дают только `alaw`; opus транскодировать или отключить | `allow=` в эндпоинте |
| Отказоустойчивость | Kamailio + RTPengine как SBC перед 2+ узлами Asterisk; состояние в PostgreSQL/Redis, узлы Asterisk по бизнес-логике stateless | новый компонент |
| Безопасность | TLS-транспорт, SRTP, whitelist IP оператора, сокрытие топологии за SBC | конфиг |
| Юридическое | договор с оператором, лицензирование услуг связи, соответствие законодательству о ПДн | вне разработки |

Ключевая мысль: переносимость обеспечена тем, что решение о маршруте принимает
внешнее приложение по данным из БД, а не dialplan. Смена транспорта — это смена
SIP-эндпоинта, а не переписывание логики.
